Additional MTP-enabled disk-cache validation on `b299af0`, RTX PRO 6000 Blackwell, ISTA IQ3_XXS, INT8 KV, 32K allocated context:

[Generic runnable probe, logs and raw results](https://github.com/CC-David-CC/Strata-a5500/tree/bench/disk-prefix-retention-20261008/docs/measurements/disk-prefix-retention-20261008).

Explicit SAVE/RESTORE worked in all four configurations: MTP off/on crossed with prefix pinning off/on. Each restore recovered all 8,191 reference tokens. With MTP on, the runtime offered and accepted drafts after restore. The reproduction uses the public engine adapter directly, with no downstream profile wrapper.

There is a separate automatic-retention issue in the same probe. After eight questions sharing that reference, switch to an unrelated request and then return with a new suffix: all four configurations report **zero reused tokens**, despite the automatic cache being below its 4,096 MiB budget. Explicit RESTORE immediately recovers all 8,191 tokens. Logs show one older snapshot dropped before the miss; checkpoint retention/supersession is a hypothesis, not yet a proven cause. #1529 was subsequently tested on this same base; the disk-only miss persists in all four configurations. [Candidate results](https://github.com/CC-David-CC/Strata-a5500/tree/bench/disk-prefix-retention-20261008/docs/measurements/disk-prefix-retention-20261008/pr1529).

The final fixture has 52 completed diagnostic generations. One MTP-pinned startup attempt hit the filesystem free-space guard before SAVE; temporary test snapshots were reclaimed and that case rerun. These are single diagnostic observations, not latency percentiles. Latest upstream main has not been tested for this failure. The issue does not require MTP, and the successful explicit restores should be distinguished from automatic conversation-cache retention.
